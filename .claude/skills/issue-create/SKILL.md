# Issue 作成ワークフロー (multiple-example)

引数: Issue の概要説明（例: 「完了済み todo を一括削除するボタンを追加」）。

## 概要

ユーザの概要説明から GitHub Issue を起票する。Issue だけ読めば実装者が着手できる粒度まで詳細設計を書き、UI 変更があればアスキーアートを含める。

### 基本方針: Issue に全て書く

- 外部リンクで済ませず、**必要な情報は Issue 本文に直接書く**
- `/issue-implement` スキルで拾ってそのまま実装に入れる状態を目指す
- 詳細設計は「実装者が迷わない程度」でよい（厳密仕様書は不要）

---

## Step 1: ヒアリング

ユーザ入力と `Grep` / `Read` でコードベースから読み取れる情報は自分で埋める。
不足分だけ AskUserQuestion で質問する。確認すべき項目:

- **Issue 種別**: `bug` / `enhancement` / `docs` / `infra` / `content` / `screenshot`
- **画面変更の有無**: UI 変更があれば Before/After のアスキーアートを描く
- **API 変更の有無**: `/api/todos` 系エンドポイントの変更があるか
- **データ形式変更**: `data.json` のスキーマに任意フィールドを追加するか
- **関連 Issue / PR**: あれば番号
- **worktree 案**: 並列作業で使いたい worktree 名の目安（`feature-xxx` 形式、任意）

---

## Step 2: ラベル決定

このリポジトリに存在するラベルのみを使う（勝手に作らない）。

### 種別ラベル（1つ以上）

| ラベル         | 条件                                        |
| -------------- | ------------------------------------------- |
| `bug`          | 既存機能の不具合                            |
| `enhancement`  | 新機能 / 既存機能の改善                     |
| `demo-feature` | 並列開発デモ用の機能追加（デフォルト推奨）  |
| `infra`        | ツーリング / scaffolding / CI 変更          |
| `docs`         | README / 使い方ドキュメント                 |
| `content`      | スライド用の文言・コピー調整                |
| `screenshot`   | スライドの穴埋め用キャプチャ                |

このリポは並列開発デモを主目的とするため、TODO 機能追加系は `demo-feature` を第一選択とする。
ラベルがなければ `gh label list` で存在確認し、なければユーザに相談（勝手に作らない）。

---

## Step 3: Issue 本文の作成

````markdown
## 背景

<!-- なぜこの Issue が必要か。ユーザ課題・デモ上の意図を 1〜3 行で -->

## 受け入れ条件

<!-- 実装完了の判定基準。具体的・検証可能な条件をチェックリストで列挙 -->

- [ ] （例）POST `/api/todos` に `dueAt` を任意で指定できる
- [ ] （例）GET `/api/todos` が過日 todo に `overdue:true` を付与する
- [ ] （例）既存 `data.json` の形式を壊さない（後方互換）

## 実装範囲

<!-- 変更対象の層・ファイルと加える変更内容を短く列挙 -->

- **API** (`server.js`): …
- **data** (`data.json` スキーマ): …
- **UI** (`public/index.html` / `public/app.js`): …
- **style** (`public/style.css`): …

## 画面イメージ

<!-- UI 変更がある場合のみ。ない場合はこのセクションごと削除 -->

### Before（現状）

```
┌──────────────────────────────────┐
│  TODO                            │
├──────────────────────────────────┤
│  [ タイトル入力_____ ] [ Add ]   │
│  ─────────────────────────────── │
│  [ ] 買い物                   ×  │
│  [x] 掃除                     ×  │
└──────────────────────────────────┘
```

### After（変更後）

```
┌──────────────────────────────────┐
│  TODO                            │
├──────────────────────────────────┤
│  [ タイトル入力_____ ] [📅日付] [ Add ] │
│  ─────────────────────────────── │
│  [ ] 買い物   📅04/15 <<<NEW>>>  │
│       [overdue] <<<NEW>>>        │
└──────────────────────────────────┘
```

## エラーハンドリング

<!-- バリデーションや異常系の期待挙動 -->

| ケース                  | 期待挙動                 |
| ----------------------- | ------------------------ |
| 不正な `dueAt`          | 400 + `{error: ...}`     |
| 不明 id の PUT / DELETE | 404 + `{error: "not found"}` |

## worktree 名案

`<例: feature-due-date>`  <!-- 並列実装時の識別用。任意 -->

## 依存

<!-- 他 Issue / PR との依存関係。なければ「なし」 -->

なし
````

### アスキーアート作成ガイドライン

UI 変更がある場合:

- **罫線**: `┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼ │ ─`
- **幅**: 40〜60 文字
- **要素**:
  - ボタン: `[ ボタン名 ]`
  - テキスト入力: `[_________________]`
  - チェックボックス: `[ ]` / `[x]`
  - アイコン: `(i)` `(!)` `(×)` `(+)` / 絵文字 (`📅` `⚠️` など)
- **変更箇所**: `<<<NEW>>>` または `*** 変更 ***` で明示

---

## Step 4: ユーザ確認

生成した Issue 本文をユーザに表示し、AskUserQuestion で確認:

- **そのまま起票**
- **修正してから起票**（修正点を聞く）
- **キャンセル**

---

## Step 5: Issue 起票

ユーザ承認後:

```bash
gh issue create \
  --title "<Conventional Commits prefix>: <タイトル>" \
  --body "$(cat <<'EOF'
<Step 3 で生成した本文>
EOF
)" \
  --label "<ラベル1>,<ラベル2>,..."
```

### タイトルフォーマット

Conventional Commits 風のプレフィックスを使う（PR タイトルと揃える）。

| 種別        | プレフィックス | 例                                                     |
| ----------- | -------------- | ------------------------------------------------------ |
| bug         | `fix`          | `fix: /api/todos の PUT で dueAt が消える`             |
| enhancement | `feat`         | `feat: 完了 todo を一括削除するボタンを追加`           |
| infra       | `chore`        | `chore: ESLint の設定を追加`                           |
| docs        | `docs`         | `docs: README に並列開発の手順を追記`                  |

`--repo` は省略可（現在のリポジトリに起票）。他リポに起票する場合のみ `--repo <owner>/<repo>` を付ける。

---

## Step 6: 結果報告

起票後、以下をユーザに報告:

- Issue URL
- 付与したラベル一覧
- 次のアクション: `/issue-implement <番号>` で実装着手できる旨

---

## 注意事項

- **ラベルは既存のみ使う**。新規作成が必要な場合はユーザに相談する
- **UI 変更がない Issue では画面イメージセクションごと削除**
- 受け入れ条件は「〜すること」ではなく「〜が返る / 〜が表示される」など具体的・検証可能な形で書く
- Issue 本文に必要情報を全部書く。外部リンクで代替しない
- 影響するファイル・モジュールは `Grep` / `Read` で実際のコードを確認してから記載する
- このリポにはテストフレームワークが無いため、受け入れ条件に「カバレッジ N%」のような指標は書かない。「curl で X が確認できる」などの形に読み替える
